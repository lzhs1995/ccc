# 协作提效与任务收尾

0.4.35在真实PostToolUse边界提示原ANSWERED全文和consume入口、待ACK握手、
握手超时及独立CALLBACK_SETTLEMENT。提示成功flush后才提交游标；它不代
正文读取、ACK、报告核收或RELEASE。结算提醒不增加下一任务ask_count，
不绕过正式预留。主管读原报告并精确disarm后，接续原计划的独立未完范围。

显式reask runner在预留、待消费回件或观察期限返回，仅释放本次调用；
新任务仍须preflight核验身份与握手，但不要求接收端空闲。终端求派从上一条原生确认后至少60秒起算，
未确认只观察原次。新投递默认30秒确认窗，reconcile默认一次只读观察；
同步I/O可能延长耗时，不以窗口耗尽归因执行者失联。详见
[0.4.35行为及证据边界](release-0.4.35.md)。

本页补充[双向投递操作规则](efficient-bidirectional-collaboration-20261004.md)，
用于决定何时协作、如何归因等待、何时收尾。以完成用户任务的效率和质量为准；
文档维护本身不要求启动 executor，也不授权更换原会话或修改在途控制器。

## 先判断能否缩短完成时间

| 当前工作 | 执行方式 |
| --- | --- |
| 没有独立待办，或派单和核收成本高于工作量 | supervisor 直接完成，executor 可待命 |
| 有一项边界清楚、可独立核查的工作 | 一个已授权且携带上下文的 executor |
| 有两项互不依赖、不会争用写入或原生资源的工作 | 两个已授权 executor，各自任务包、nonce、输出目录 |
| executor 持续失效且已有自动接管授权 | 固定检查点并确认无并发写入后，supervisor 继续 SOLO |

先备好具体任务再握手。不要为了让两个窗口保持活跃而重跑已通过检查、
重复读相同证据或把同一个待办发给两人。共享源码只有一个写入者；
独立审查者先读取冻结输入，修改后只审必要增量。共享 UI 资源仍按原协议串行。
等待回调期间，supervisor 推进不依赖该结果的工作。

### 握手通过后必须接上具体派单

握手前备好业务范围、真实输入和验收条件；ACK 后只补本次身份凭据，随即
finalize 并提交任务包。握手 PASS 但任务包仍为 draft 或尚未提交时，记为
`SUPERVISOR_DISPATCH_PENDING`，由主管完成交接，不能归因 executor 故障。
分别保留 ACK、定稿、提交和消费的实际时间；缺失项保持未知，不补造时间。
压缩接续或用户催进度时，先处理这个已有待办，不重复健康握手；已经提交的
原尝试仅做只读核收。既有任务真正结束并核收后，再按独立待办衔接下一单，
不让维护占住派单，也不把新任务堆进正在执行或压缩中的会话。
这是主管调度规则；未接入运行时检查前，不称已有自动派单 hook。

### 哨兵启动失败先核角色表格式

`SENTINEL_ROLE_MAP_REFUSED` 是监控启动失败，不能据此判断 executor 失效或
重发业务。`cmux_executor_sentinel.py` 同时消费 harness 的 `surface_ref`、
`executor`/`executor2`，以及协议角色表的 `identity`、`executors[]`；一个哨兵
只观察 argv 指定且属于该任务的执行者。多个声明必须一致，缺少执行者、
冲突别名、executors 列表重复角色或同一 surface 占据多个角色均拒绝，不取第一项凑成功。

用生产者实际输出及协议形状做离线正反例，并通过 `main` 确认冲突在启动
daemon 前拒绝。角色表解析成功只证明文件与参数一致；实时 caller、workspace
和 UUID 仍由原传输门禁核验，不能据解析结果跳过握手或宣称监控已运行。
固定在途任务保留原包和已核适配器；源码发布不热替换已运行的哨兵。

### 让有界审查真正可收尾

任务包列出的 role-map、inventory 和输入证据必须指向实际文件；缺少的可选
资料应明确标为未提供，不能用占位路径冒充已生成的身份凭据。已派发任务包
保持原绑定，发现问题写核收记录，不能为补附件而改包或重新握手。

审查输入分为固定快照和 supervisor 正在维护的入口。固定快照记录路径、SHA
及范围；活动入口明确其所有者和观察时间。执行者只复查影响结论的入口变化，
不因主管已修复导航而重新审计整条链。主管逐项注明已采纳、已被后继修正、
证据不足或不属范围，继续剩余产品工作，不为积累协作经验追加另一轮审查。

区分执行者的主观观察与传输证据：“没有看到派单提示”不证明零发送；应核原
attempt、完整接收记录和任务包绑定。旧固定 skill 的接口差异也不能推广为当前
安装故障；先核其版本及实际命令，再更新面向后续任务的文档，保留在途控制器。

### 接续任务时先核实际归属

上下文摘要里的原 supervisor/executor 绑定可能与当前工具 caller 不同。
先把实时 caller、workspace UUID、原 role-map 和执行者当前任务对齐；
focused 面板、`EXECUTOR` 标题或同目录不能证明它属于本任务。
只读看到执行者正在处理另一份任务包时，记录“另有在途任务”，不插队派单、
不撤销它的任务，也不把它记作故障或空闲。原绑定在其他工作区时，保留原绑定，
按已有 SOLO 授权继续可独立推进的工作，不改环境身份或借用其他项目的执行者。

状态更新须说清当前使用零、一或两个执行者的具体原因，并区分“没有派单”、
“另有任务”、“身份不匹配”和“本任务执行失败”。只在下一次实际派单或已有阶段边界
重新核实可用性，不为证明 agent 活跃建立额外轮询；不能永久沿用过去的失败判断。

## 握手预算与准确归因

- 初始挑战直接提供绝对 pending receipt 和固定完整 SKILL 路径；握手只验证
  身份、通道及精确 ACK，不包含业务审计、全盘搜索或计划共识。
- 使用相位参数 `--handshake-timeout 600` 或更长预算；不要用泛化
  `--timeout` 覆盖各相位预算。600 秒是观察预算要求，不是强制等待：
  合格 ACK 一经观测就继续。健康的同任务握手复用。
- 分别保存 dispatch 提交、首次观测、ACK、检测终态时间及 budget_source、
  phase_minimum_seconds、ack_source。预算不足记
  `SUPERVISOR_BUDGET_TOO_SHORT`，不能记为 Claude 不响应。
- ACK 文本相同但 ack_line/ack_source/ack_observed_at 为空，只能说明检测器
  未观测到该 ACK，不能推定格式拒绝或执行者失效。先核原 task/nonce 的真实记录。
- 原绑定允许迟到 ACK 核收时只读恢复；已终态且不支持恢复时，保留失败，
  由原控制器在明确零输入或原发送已安全收口后建立后继。不要向旧 nonce 空转重发。

## 双向发送与回调收尾

### 探针清理与ACK等待的可执行后置条件

从0.4.46起，普通preflight直接握手，不执行bridge-test，不要求暂停原生/goal。
就绪prompt应通过支持入口及时双向投递；接收方自行协调执行次序。详见
[忙碌时双向通信](busy-bidirectional-communication.md)。

仅显式诊断的bridge-test为每个executor生成独立短探针（如`B1_<8位随机十六进制>`），
实际token与task/ordinal/UUID一起记录，不从task id猜token。短探针减少逐键
删除次数；每次按键仍过实时身份门禁，600秒ACK预算不缩短。离线通过只能
证明回归场景，不得把少按几次键称为现场握手耗时或成功率测量。

完整token消失不等于输入区已空：它可能只删掉了一部分，也可能读屏暂时没有
prompt glyph。清理只删除保守解析后明确属于本token的非空前缀；其他文字、
排队/运行状态或缺glyph仅做有限重读。最终必须观察到空compose；已有显式
force授权的虚拟建议场景，只能恢复到实际粘贴前的文本，不能拿更早的输入
区作证。未确认就保留失败，不自动扩展force授权、不盲删或提交下一条消息。
每轮记录读屏SHA、是否读到compose、归属判断、删除数量和确认依据。

已发送并等ACK、以及检测器未确认后观察原nonce时，顶层receipt须为
`AWAITING_EXECUTOR_ACK/PENDING`，不得提前写FAIL或终态error；原传输异常
仍保留在dispatch_error。多executor部分ACK不能PASS。实际拒绝、期限耗尽
或无效状态才记录对应FAIL；原`validate`仍要求所有executor精确ACK。

这些约束在harness及其回归测试中执行，不另建第二个发送器或轮询器。固定
在途任务继续用原控制器；新安装入口、进程已加载版本与真实握手分别验证。

有完整边框的 Claude 编辑区与边框外状态栏须分别解析；只有已知模型行和
已知 footer 形状才能排除状态栏。用户在编辑区内输入相似文字仍是草稿。
空编辑区不等于接收端空闲：`◐ Bash: ...` 等实际运行状态仍拒绝诊断探针和
删除，包括已获 force-compose 授权的调用。这些清理条件不限制无探针的新握手
或普通通信；原失败探针的专用恢复仍保留原控制器要求。

原探针已发送、清理未确认且尚无 handshake/task-pack 时，可由真实主管调用
`bridge-clear-observe --bridge-clear-recovery /absolute/task/new-observation.json`。
它只读当前界面、核原任务及单执行者身份，并独立保存空闲/空输入区观察；
不发送或删字，不改原失败。后继 `handshake` 显式使用同一路径，重新核当前
身份和空闲状态。原始哈希变化、草稿、运行/排队、未知界面或已有握手都拒绝。
这不是重跑 preflight 的许可，也不能补造回执使真实 caller 认证失败通过。

prompt 和 callback 均遵循[原生投递与有界等待](verified-compose-delivery.md)：
输入前固定同一接收进程/session/transcript 和新鲜 EOF fence；新 Codex 输入
持久化 NATIVE_INPUT_INTENT，Claude 终端输入保留 PASTE_INTENT；
只有边界后新增、全文完全相等的 native user 才为 `NATIVE_RECEIVED`。
空白和换行不得改写。屏幕、ACK、Enter/Tab、退出码与空 compose 不证明收到；
Claude `queued_command` 仍 pending。执行、正式 receipt 和业务接受另列。

新 Codex 消息及 callback 通过原 thread 的认证 control socket 直接输入：
活动轮只调用一次 turn/steer，空闲原会话只调用一次 turn/start；不读写 composer，
不粘贴、不按 Enter/Tab、不进入 queued follow-up inputs。异常或未知只观察
原日志，不重试或降级排队。历史 queued callback 留在原 controller，不能原生重放。
Claude 首次粘贴一次，完整草稿及结构连续两次稳定后提交一次；历史终端恢复先核
迟到原生记录，自动/显式路径共用一次补键，意图落盘即消耗。未知、排队、草稿
改变或缺原 binding/fence 不补键，不重贴或追补旧基线。

executor 完成报告后调用原 callback 入口，由它判断输入条件；
不得额外等待 supervisor 的 busy=false，也不另建秒级 watcher。
若回调传输待核，supervisor 可先读取固定报告推进业务，保留“正式回执缺失”；
不能制造 receipt 或把维护等待扩大成所有工作停摆。旧任务的 disarm
仍遵循原操作规则的真实终态与证据要求。

## 有界恢复与安全接管

分别诊断 provider 故障、监督端预算不足、输入分类器拒绝、草稿保护、
排队和 ACK 漏观测。后三类不是模型失效，不能靠换模型、重启会话恢复。
原生 reconnect 或原请求仍在执行时不叠加该请求的外层重试；新消息就绪后仍
由支持入口判定能否输入，不因对方忙碌而等待。原请求重试只在其确已结束后
遵循既有有限恢复协议。认证、欠费不盲重试。

持续不可用时沿用户已有授权：保留原会话和未决尝试，停止本阶段派单，
确认 executor 无在途写入，固定 checkpoint、nonce 和保护路径，由 Codex
接管。自审标 `solo_self_review`，不能冒称 Claude 独审。只在同一会话、
安全写入边界交接写入；恢复联络本身无需等待该边界，不能用清空上下文或替代 executor 绕过。

## 完成后及时收口

### 核收后把结论和下一步交回执行者

`REPORT_READY`、原回调已核收、业务已接受、等待依赖和 provider 故障分别记录。
旧 `CALLBACK_UNCONFIRMED` 或自动 recap 只代表当时状态；用户看到停止时，先读
原报告、原回执、disarm 记录及当前屏幕，不用旧终态推断崩溃，也不重做旧任务。
压缩仍有实际进展时保留原会话，按既有故障证据门槛判断是否需要恢复。

主管完成核收及安全 disarm 后，在原任务旁写追加状态：任务及证据路径、业务
裁决、回调状态、下一动作、负责人和触发条件。可执行的独立待办及时正式派单；
缺同版 PDF 等真实依赖时明确 `WAITING_DEPENDENCY` 及生成者，由主管继续主线。
没有独立待办无需造新审查，子任务结束也不能冒称整个用户目标完成。

状态就绪后，用现有受保护 bridge 及时同步；无需等待接收端空闲。可合入真正
需要的下一任务交接，不额外要求 ACK 或握手。通知有自己的原 attempt：compose、
queued、消费和确认仍分别记录。通知未确认不撤销已核收的旧 callback，也不
重发通知、补 Enter 或重开旧 callback 探针；主管继续独立工作。

收口状态只描述原任务的责任与证据，不能封锁 armed 或普通会话的工具及 Stop。
新的用户查询和已授权主管通知可正常读取核收证据、回答当前状态；旧报告、
marker 与原回调保持原样。已授权求派使用显式入口或独立登记的文件调度，
不由 Stop 强迫回合，不让用户代为转话。状态消费、后继派单与恢复业务分别验收。

若正式回执已确认、业务已有裁定且原 marker 已解除，执行者仍在新的回复中
重复旧 `CALLBACK_UNCONFIRMED`，这是状态叙述未更新，不能写成静屏、当前 hook
仍封锁或 API 连续失败。保留原发送尝试中的失败观察；后继有效回执与裁定负责
说明它如何收口，不把旧 attempt 改为成功，也不重复结算或 disarm。

`executor-availability.json` 的 `ACTIVE` 属于可用性/接管状态，不是任务未完成
的证据；没有完成态的契约不能手工补 `COMPLETED`。主管一次状态通知直接绑定
已存在的回执、裁定和解除记录，执行者按当前证据回答。若新的有权工具调用仍被
拒绝，才核实际 hook 输入、拒绝原因与加载版本；配置和源码相同不能证明本次
调用已通过。没有真实未决依赖就不另造任务来刷新屏幕。

`disarm` 真实移除 marker 后会给出条件提示
`next_action=SUPERVISOR_STATUS_SYNC_IF_STALE`。它仅提醒上述一次通知，不声明
当前仍有阻塞，不自动发送，也不增加确认门槛；重复调用且 marker 已不存在时
不生成新同步动作。通知本身不能证明工具恢复或业务验收。

收尾规则见[执行者交付后收口](executor-closeout-enforcement.md)。报告、任务包和
原记录按原证据契约保留，由显式诊断及原 controller reconcile 核收。
全局 PreToolUse/PostToolUse/Stop 使用同版非阻断 observer；不运行旧 gate，
不返回 deny、block 或 continue:false，不强迫重试。未证实的收到或共识不得
宣称，但真实性要求不依赖封锁会话。未知回调交原主管核原次。

定点失败、必要增量回归、真实效果、用户验收分别留证。用户已验收的
局部故障即在账本结案，剩余主线另列；没有新变更或未决风险就不重跑旧矩阵。
状态更新说明完成了什么、尚缺什么、下一项具体动作，避免只堆测试数量。

经验进入仓库时只写可复用规则，不公开 Key、用户原日志或本机身份。
源码提交、CI、安装、客户端加载、真实投递及整体验收各自报告；
修改本页不代表新 hook 上线，也不需要重启正在工作的客户端。

## 有界发现报告与等待

主管用 `scripts/cmux_supervisor_report_guard.py` 经认证 active markers 有界发现
本 workspace 的原冻结报告；该检查器不是已注册的自动 PostToolUse。
自动 observer 只在实际线程的工具边界提供最多8条文件请求，公平轮转、成功
flush后提交游标；child不能消费parent收件箱。发现不等于读取、送达、接受或 disarm。封口
诊断使用 `scripts/cmux_callback_diagnose.py --task-pack <原绝对路径>`，
不发送输入，不改原证据。正式接口须来自完整相容安装。

idle Stop 只持久化一次状态并允许结束；未求派不能拦截 Stop。
显式 `executor_ready.py persist` 仅读原请求/答复，最长 300 秒。
未确认保持同一 payload、marker、nonce，不每 60 秒重贴，不因重启延长
期限。CCC 等待主管同步终态和期限；native Goal 单独核证，不能由配置
落盘或 hook 放行推断。详见[统一合同](verified-compose-delivery.md)。

## 文件协调与磁盘受限时的接续

跨工作区的既有文件请求也是待办入口。接续时先读取原请求、追加请求、结果和
回件，再决定是否需要联系对方；记录实际读到的文件身份和处理范围。回件已落盘、
对方已读取、对方已接受分别记账。旧交接里“无回复”的句子不能覆盖较新的核收。
固定旧回复保持原字节，补充发现写独立后继；不为补一次文件回件重新握手或开审。

当用户要求保留最低可用空间时，检查文件系统实际可用字节及下一阶段的空间预算。
不足时暂停新增大产物，继续可独立执行的小文件整理，并主动处理已获授权的备份
和清理。上传完成不等于可删源：先核实际回下载的整包和全部内容，再核源文件
身份、在途句柄及依赖。备份者与源文件所有者不同，按原责任分别记录云核收和
源回收；再次清理前先读所有者回执。源已由所有者移除时，不重放删除、不据缺失
直接报文件损坏；核原回执后只处理自己有权处理的终态缓存。

逻辑文件大小、allocated、APFS克隆或硬链接大小不能预测实际回收量。记录清理
前后的整机可用空间，存在并发写入时不把全部差额归因本任务；压缩也可能先增加
占用。一次压缩没有释放空间时保留事实，不批量重复相同操作。不得据旧云回执
删除身份不同的新文件，也不得删除唯一原件、活动数据库或必要运行依赖。

这是使用既有授权推进工作的规则，不新增删除权限或常驻轮询器。零、一、两个
执行者的选择继续由独立待办和真实可用性决定；caller身份歧义本身不证明执行者
故障。保留原会话，按既有SOLO授权继续，下一次有实际派单需要时再核身份。

### 接管会话时的当前身份与主线进展

继承的业务 session、当前执行 thread 与当前原生客户端分别记录。只匹配启动时
的 resume 参数会漏掉新建或切换线程；用原生 foreground 选择加内核身份和
实时 UUID 核验，不能借旧 surface 或改环境变量通过。身份识别失败是主管本地
故障，不能称为 Claude 失联；已有 SOLO 授权时继续独立业务，恢复后及时联系
原执行者并派有独立交付物的工作，不以忙碌拒绝联络。同 pane 两个 tab 的输入始终串行。

更新的原生 API 成功、新回合和真人接管优先于历史错误及旧等待。发布验收分别
记录源码测试、不可变安装、稳定性、自动 hook 和完整原生接收；通过一项不能
代替其余项。旧 callback 预算已耗尽时保留未确认，不重放、不伪造核收。

## 不让文件求派依赖持续占用回合

0.4.27 的独立 launchd 文件调度按显式认证登记每60秒更新请求，最多256个登记，
单次sweep最多10秒，忙锁跳过。登记绑定原task/purpose/workspace/controller，
不迁移旧episode；file-only不读转录或旧idle binding、不调用发送器。
只归档真实episode转换，保留UNKNOWN及原pending。安装、登记、实际执行、
hook提示和主管正文读取分别验收；该调度不能唤醒空闲模型。主管按原模板回
mailbox，再核新派单边界；不重复已接受callback，不重开科研审轮。

### 同一 pane 的原生 Codex 维护通信

0.4.28 的 `successor-rebind-v2` 可显式固定 `transport=codex_native_same_pane_v1`。
授权记录与 artifact 必须同时绑定不同的 `caller_thread_id`、`target_thread_id`，
以及双方 workspace/surface/pane UUID。只允许同工作区同 pane 的两个不同 surface。
调用者必须通过当前原生 foreground 线程认证，接收者必须仍是指定 Codex 进程和线程。
随后沿已认证 control socket 单次 steer/start，保留原 EOF/NATIVE_INPUT_INTENT；
接收不确定只观察原次。此授权拒绝全部终端 paste/send/key，也不放宽普通侧窗格规则。
旧 controller、回调与 UNKNOWN 不迁移。安装、自动 hook 与真实原生收发另行验收。

### 继任握手的时间与证据

- 对既有 Claude 明确指定 `--executor claude`；默认 provider 不能代替已核实的进程类型。
- 在原绑定 mailbox 回应继任身份、用户授权与下一步；正式 preflight 不要求
  等待对方结束回合或暂停Goal。原通知仍按原次处理，不用新 nonce 重放。
- 同工作区发送与取相同锁的 reconcile 串行；只读不代表不占发送锁。
- 迟到 ACK 先查原 receipt。已有 receipt 时复用原 provider/task/nonce 严格解析，
  保留旧超时证据并重算 validation；不重复 submit，也不删除 receipt 规避拒绝。
- 分别记录原生收到、执行者真实 ACK、主管观测和解析时间。主管晚核收的时间
  属于主管延迟，不能记成 Claude/API 故障。ACKED 与旧 timeout 字段可同时作为历史
  证据保留；当前决策以真实 ACK 与 validation 为准。
- ARMED 表示任务登记。当前 advisory hook 放行普通工具与 Stop，业务接受仍需
  显式独立审阅；不能再宣称 Stop 会阻断等待共识。

### 在任务边界及时交付

每单预先固定一个可核收问题、输入版本、输出路径、必要检查与停止条件。
完成能回答该问题的检查后先交报告；只有新修改、失败或具体未决风险才扩大或
重复回归。不能因等待旧回调、发布或别人的报告而反复审查已接受的范围。
达到本单约定预算而仍未完成时，交已验证结论、未决项及下一步的阶段报告，
由主管按原范围继续处理；不把持续测试或写进度文件当作交付。

收到绑定回复后，在下一个实际工具边界读取全文并按原控制器精确消费。
ANSWERED 未消费和正式 reservation 期间不得反复求派或自设重复唤醒。
原生 Goal、用户 /loop、CCC 与协作 advisory 分别取证；旧 callback 或共享
维护发布未闭合，不能自动成为强迫业务继续轮转的理由。两轮消费功能通过
仍需单列检测到消费的时效；文件 scheduler 没有唤醒空闲模型的能力。

Claude 队列中的 remove 或 queued_command 附件只证明客户端处理过排队内容，
不保证将来出现整串相等的 native user。按原 fence 有界核查后仍未证，就保留
未证；真实 ACK 可以另行核收，不能反向补造通知收件或授权重发。已有授权的
维护文件提示沿原 enrollment 使用，正式业务仍需原控制器的派包与验收门禁。
原生Goal/loop持续运行不应阻止握手和新消息，不能要求停用自动续轮来制造
通信窗口。双方prompt就绪即通过支持入口发送，具体执行次序由双方协调。
保留真实草稿、原次去重和共享写入归属，不清空队列或替换原会话；
实际客户端无法输入时报告该次原因，不把忙碌一概判为不可通信。

### 空间不足时保持推进

按用户原始要求保留至少10GB（10,000,000,000字节）；低于20GB
（20,000,000,000字节）即触发主动管理与备份，20GB不是安装硬底线。
安装须另计源码、临时文件与回滚预算，预计完成后仍保留至少10GB。
低于20GB时沿已有串行百度 consumer
备份终态缓存，回下载核整包SHA及全部成员后才按原权限释放；核实际卷free变化。
不因磁盘不足结束总任务，继续源码、文档和独立核验。保留原件、活动数据库、
原会话、失败证据和系统swap，不启动第二consumer，不降低既有传输门槛。
