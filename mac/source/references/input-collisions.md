# 终端发送冲突与原次恢复

握手探针、正式派单、普通消息和自动续跑共享同一个真实输入框。
0.4.29 给不提交的握手探针补齐既有正式发送的 pane/target 互斥。
旧控制器不迁移；是否已安装及后台发送器是否采用同一锁，必须分别验证。

所有自动终端写者先取得同一用户状态根 `~/.local/state/multi-agent-collaboration/deliveries-v1` 下的两把 exclusive nonblocking flock，顺序固定：

1. `pane-<sha256(workspace_uuid + ":" + pane_uuid)>.lock`
2. `target-<sha256(surface_uuid)>.lock`

UUID 采用经过认证的绑定原字节，与原发送器一致，不另行大小写转换。
锁文件不删除、不替换。持锁范围覆盖最后空输入检查、一次粘贴、完整稳定草稿
回读和受支持的提交键，探针覆盖完整键入/清理。不得持锁等待模型回答。
争用时零输入返回并在空闲边界续办，不能借此锁住用户普通工具或会话结束。

互斥只协调采用同一合同的写者，人仍可能随时输入。每次提交仍须逐字核对整个
当前草稿；历史正文、子串、提示文字相似或任务 nonce 都不能授权 Enter。
CCC/其他后台程序的锁接入由其唯一维护者处理，协作安装不证明后台已加载。

发现碰撞时保存原attempt、原生绑定/EOF fence、完整草稿和另一写者事件证据。
只定向静默受影响的自动续跑通道，保留原会话和正在执行的任务；先确认活跃
健康记录真的报告暂停，再继续原主管的串行派单。启动时生成的runtime文件可能
不会随热配置更新，须核实际观察记录而非仅看旧配置mtime。

- 混合草稿尚在输入框：原次只读核收；不清草稿、不重复粘贴、不改nonce。
- 另一写者已提交混合正文：保存原生完整记录和偏移。混合记录不等于原通知的
  精确 `NATIVE_RECEIVED`，不篡改旧回执。若原执行者已读精确pack并开工，沿
  原任务审阅其材料和报告，另记读取/业务接受证据，不为补回执重派。
- 原通知真正逐字入站：沿原控制器零输入核收。无需再握手或重发。

解除静默前核同锁采用、完整草稿保护和真实健康状态；仅按原授权恢复那两路。
这种定向处理不改变正常继任握手默认允许规则，也不转交旧callback所有权。

版本升级还须逐项核 configuration-guardian 和 executor-reask-scheduler 两个独立
launchd作业，doctor检查两者是否指向CURRENT。实际注册、真实60秒运行、原执行者
明确登记、读取回件和consume分别留证；不能用hook更新代替scheduler更新。
已登记旧控制器不迁移，新升级在原授权任务边界协调原执行者登记。
