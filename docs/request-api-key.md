# API Key（最近请求）

CCC 的 `api-key` 列展示与该会话及进程身份匹配的最近一次请求观测，不读取当前全局配置来填充这一列。请求已尝试发送不等于服务端已接受，也不保证下一次请求仍使用同一 Key。

| 显示 | 含义 |
| --- | --- |
| Key 值 | 已核实当前会话的请求记录及对应进程身份。 |
| 历史请求（K查看完整值） | 历史观测，仅用于追溯，不能当作当前进程的请求证明。 |
| 暂无请求记录 | 尚无符合要求的请求记录。 |
| 仅旧进程记录 | 找到了旧进程的记录，不能归给当前进程。 |
| 未接入采集（K查看） | 当前 Claude 进程未接入请求采集；重新打开 CCC 不会给已运行的 Claude 补装采集。 |
| 未核实 | 身份、记录或读取一致性未通过核验；不以全局 Key 代填。 |

## Codex：配置与实际请求

修改全局或项目 `config.toml`，不能证明已经运行的客户端采用了新凭据。启动参数、环境及客户端配置来源也可能不同。CCC 按实际客户端的观测目录和发送进程身份核实请求，而不是按面板自身的配置推断。

混合 Key 是否生效，应比较各会话新的实际请求记录。仅旧进程记录或暂无记录，不足以判断冷切换失败。遇到普通 prompt 与 `/goal resume` 使用不同凭据，应分别核查两次请求的会话、进程及凭据来源；不能仅凭错误提示认定该命令修改了全局配置。

## Claude Code：全局配置与独立 profile

全局配置的变化和 `ccp-new` 独立 profile 可能产生不同凭据来源。面板依据请求边界采集的实际认证头展示结果，不假定所有 Claude 共用当前全局 Key，也不将 profile 文件内容直接当作请求证明。

如果同一次请求的 Bearer token 与 `x-api-key` 不同，分别展示两者。观测结果仍只是该次请求使用的凭据，不能证明后续热切换已经生效。

## 已运行客户端的升级

重新进入 CCC 只更新面板，不会重启或改造原有客户端。旧客户端需要在保留原 session、环境及配置的条件下接入采集，再由真实请求形成观测。不要为了消除“未核实”而强制退出原会话或发送额外模型请求。

原会话恢复方案会校验历史及配置绑定；历史追加后，旧方案可能失效，需要在安全的升级边界重新生成，不能跳过校验。没有当前请求证据时，保留准确的状态比展示另一个进程或全局配置的 Key 更可靠。

## 已解决案例：后台角色误判导致 surface:46 无法显示 Key

2026-10-07，用户确认 `workspace:15 / pane:33 / surface:46` 的 `api-key` 列正常显示，本故障项完成。固定 surface UUID 为 `5CDB0F6A-078F-4034-8D45-45EB99D5D68F`，验收绑定原 session `01a0e96a-68dd-7210-8ef0-d83c89dca4d8`。此次修复不需要退出原 Codex 会话或重新配置 Key。

根因是受管理的 `app-server` 继承了 `CODEX_CLIENT_THREAD_OBSERVER`，但不负责发布 TUI 前台选择记录。旧解析器把后台缺少该记录误判为整个客户端无效，因此遮蔽了健康前台及已有的实际请求 Key。

修复按精确的 `argv[1] == "app-server"` 识别后台角色，重复核对 PID、出生时间和 argv，并在发布前重新确认角色。前台选择与后台请求分别承担各自的证据责任；仅有后台记录仍不足以代替当前前台身份。实际请求身份不符、记录漂移或只有旧进程证据时，继续拒绝显示为当前请求。

后续同类排查遵循以下顺序：

1. 固定 workspace、surface UUID、原 session 和 PID/出生时间，避免把位置变化或进程替换混为 Key 变化。
2. 先区分前台与后台职责，再检查各自应发布的观测；继承采集环境变量不等于承担相同发布职责。
3. 将显示值绑定实际认证请求头及当前请求身份，不使用全局配置或旧进程记录填充缺口。
4. 分别确认运行版本安装、面板加载与实际请求显示。已接入采集且身份连续的原会话，不因面板显示异常而被强制重启。
5. 用定点回归、实际请求原件和用户界面验收闭环；通过后保留失败记录，不重复旧矩阵或额外发起模型探针。

证据位于 `verification/ccc-collaboration-efficiency-20261004-01/post-submit10/`：636 修复原件记录 64 项定点及 390 项候选测试通过（`solo_self_review`）；656 确认原进程与 session 连续且请求状态为 `observed`；659 只读检查再次确认 Key 与实际请求匹配、未使用配置值。660 完成回执绑定上述原件及用户验收。

该结论限定于 surface:46 显示故障。659 的全体覆盖仍为 19/24，其他覆盖缺口、续跑性能及 UI50/500 验收保持各自状态。
