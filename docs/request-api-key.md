# API Key（最近请求）

CCC 的 `api-key` 列展示与该会话及进程身份匹配的最近一次请求观测，不读取当前全局配置来填充这一列。请求已尝试发送不等于服务端已接受，也不保证下一次请求仍使用同一 Key。

| 显示 | 含义 |
| --- | --- |
| Key 值 | 已核实当前会话的请求记录及对应进程身份。 |
| 历史请求（K查看完整值） | 历史观测，仅用于追溯，不能当作当前进程的请求证明。 |
| 暂无请求记录 | 尚无符合要求的请求记录。 |
| 仅旧进程记录 | 找到了旧进程的记录，不能归给当前进程。 |
| 未接入采集（K查看） | 当前 Claude 进程未接入请求采集；重新打开 CCC 不会给已运行的 Claude 补装采集。 |
| 未核实 | 身份、记录或读取一致性未通过核验；不以全局 Key 代填。 |

## Codex：配置与实际请求

修改全局或项目 `config.toml`，不能证明已经运行的客户端采用了新凭据。启动参数、环境及客户端配置来源也可能不同。CCC 按实际客户端的观测目录和发送进程身份核实请求，而不是按面板自身的配置推断。

混合 Key 是否生效，应比较各会话新的实际请求记录。仅旧进程记录或暂无记录，不足以判断冷切换失败。遇到普通 prompt 与 `/goal resume` 使用不同凭据，应分别核查两次请求的会话、进程及凭据来源；不能仅凭错误提示认定该命令修改了全局配置。

## Claude Code：全局配置与独立 profile

全局配置的变化和 `ccp-new` 独立 profile 可能产生不同凭据来源。面板依据请求边界采集的实际认证头展示结果，不假定所有 Claude 共用当前全局 Key，也不将 profile 文件内容直接当作请求证明。

如果同一次请求的 Bearer token 与 `x-api-key` 不同，分别展示两者。观测结果仍只是该次请求使用的凭据，不能证明后续热切换已经生效。

## 已运行客户端的升级

重新进入 CCC 只更新面板，不会重启或改造原有客户端。旧客户端需要在保留原 session、环境及配置的条件下接入采集，再由真实请求形成观测。不要为了消除“未核实”而强制退出原会话或发送额外模型请求。

原会话恢复方案会校验历史及配置绑定；历史追加后，旧方案可能失效，需要在安全的升级边界重新生成，不能跳过校验。没有当前请求证据时，保留准确的状态比展示另一个进程或全局配置的 Key 更可靠。
